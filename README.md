# Semantic TextNavigator

Браузерное приложение для проверки суммы и срока поставки с цитатами исходных TXT. Расчёт выполняется на клиенте, backend и платные API не нужны.

## Запуск

Откройте GitHub Pages либо раздайте каталог любым статическим HTTP-сервером, например `python -m http.server 8000`, и откройте http://localhost:8000. Runtime-зависимостей и ключей нет. Открытие index.html через file:// не поддерживается из-за ES-модулей.

## Использование

Загрузите свои TXT (до 2 МБ каждый), задайте дату проверки и проверьте таблицу. Четыре вопроса доступны в отдельной вкладке. Откройте значение для просмотра основания и точной цитаты. Письма и проекты показаны отдельно от действующих условий. IndexedDB сохраняет комплект в текущем браузере; его можно очистить в интерфейсе.

## Архитектура

File API → загрузчик/версии/SHA-256 → парсер и терминология → правила по полям → отдельный валидатор → UI. IndexedDB хранит исходники, но анализ при восстановлении пересчитывается. Модули в src разделяют загрузку, хранение, разбор, правила, валидацию и интерфейс.

## Ограничения

Поддерживается ограниченный класс русских TXT с явными реквизитами, датами и текстовым статусом подписания. Это не проверка юридической подлинности подписи. Неоднозначности требуют ручной проверки. Нет OCR, PDF/DOCX, рабочего календаря, серверного хранения и синхронизации устройств. Общие примитивы парсера и валидатора сохраняют риск совместной ошибки. Документы пользователя не отправляются на сервер; учебные материалы и внутренние отчёты в публичный репозиторий не включены.

## Продуктовая записка
# Продуктовая записка



### Пользователь и гипотеза

Закупщик восстанавливает актуальные обязательства по комплекту договорных документов. Ему нужны сумма, срок и возможность быстро проверить основание. Гипотеза: структурирование условий с цитатами сокращает ручной поиск, сохраняя контроль человека над сомнительными случаями. MVP не устанавливает юридическую действительность подписей: проверяет явно указанный текстовый статус.

### Пять вопросов заказчику

1. Какие шаблоны, языки, валюты и объёмы документов встречаются чаще всего?
2. Чем подтверждается подписание в реальном процессе и где хранится достоверный реестр подписей?
3. Как различать договоры с повторяющимися номерами: дата, стороны, организация, внутренний ID?
4. Кто и как разрешает противоречия, выбирает исправленную версию и фиксирует решение?
5. Какова цена ложного подтверждения, требования к времени проверки и права разных пользователей?

### Допущения и метрики

Поддерживается русский TXT общего формата исходников: заголовок в первых двух непустых строках, номер договора, явный `Статус: подписан… обеими сторонами`, дата документа, поставщик после `Поставщик:`. При отсутствии отдельной даты подписания используется дата явно подписанного документа. Исходный договор действует с даты документа, если не указан отдельный порядок вступления в силу. Изменения требуют подписанного допсоглашения с известной датой действия. Каждое поле имеет свой приоритет; дата/имя загрузки его не меняют. Два различных соглашения одного дня с противоречивыми значениями требуют проверки.

Метрика качества — доля автоматически подтверждённых условий, совпавших с независимым эталоном и имеющих корректное основание; отдельно считаем ложные подтверждения. На исходном наборе проверяются пять подтверждённых сумм/сроков и одно отсутствие суммы, цель — ноль ложных подтверждений. Это небольшой контрольный набор, не оценка точности на всех договорах. Метрика полезности — время получения и проверки суммы/срока закупщиком против ручного процесса на одинаковых задачах. Пользовательский замер не проводился, ускорение не заявляется.

### Архитектура и три решения

`File API → SHA-256/версии → абзацы/терминология → кандидаты → связи/правила по полям → независимая валидация оригинала → таблица/цитаты`. IndexedDB хранит байты, версии, поля, связи и результаты, но восстановленный анализ всегда пересчитывается. При недоступности хранилища работа продолжается в памяти с предупреждением.

1. **Детерминированные правила вместо LLM.** Бесплатный воспроизводимый запуск и проверяемые основания; меньшая полнота на незнакомых конструкциях. Неизвестная формулировка означает «Требуется проверка», а не доказанное отсутствие значения.
2. **Два разделённых контура.** Валидатор не вызывает парсер: сверяет цитаты/позиции, независимо читает статус и даты, контролирует нормализацию и пропущенное более приоритетное основание. Часть низкоуровневых функций дат и реквизитов общая; это снижает стоимость MVP, но сохраняет риск общей ошибки. Абсолютная точность не гарантируется.
3. **Браузер + IndexedDB.** Нет внешней передачи документов и серверной БД. Компромиссы — локальность одного origin, квота браузера, отсутствие общего аудита и синхронизации вкладок. Исправленные версии выбираются явно; все исходные байты сохраняются.

### Масштабирование и следующий шаг

При 100 000 документов нужны объектное хранилище оригиналов, БД документов/версий/связей, индексы реквизитов и полнотекстового поиска, очередь фонового анализа с версией правил, инкрементальный пересчёт, API с авторизацией и проверкой доступа к каждому источнику. Добавляются ролевые права, изоляция организаций, аудит решений и наблюдаемость; обработка больших наборов уходит из UI. Эти механизмы в MVP не реализованы.

Приоритеты развития: (1) независимый размеченный корпус и расширение проверяемых формулировок; (2) рабочий процесс разбора конфликтов/подписей с аудитом решений; (3) фоновые обработчики и контролируемые интеграции с реестром документов.
